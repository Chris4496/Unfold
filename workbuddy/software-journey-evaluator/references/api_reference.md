# 任務契約、報告與評分格式

本檔是純文字工作模板；每次評估另產報告，不在技能檔內存放私人資料。所有結論須注明來源：需求主張、程式碼線索、實際 UI／API 觀察、合成測試事件，或真人反饋（如有）。

## 1. Agent 1 的審批前報告

標題：`[產品] 旅程分析報告 v[版本]（待委託人確認）`

1. **評估邊界**：產品版本、資料來源、可操作環境、不可測範圍、敏感風險。
2. **流程圖及狀態**：起點 → 行動 → 判斷 → 例外／取消 → 終點；每步標明「文件主張／已實作並可觀察／未知」，不可把兩者混同。
3. **角色與交接矩陣**：誰發起、誰接收、發生在哪個產品功能、何時被授權、可以看到甚麼、不應看到甚麼、失敗時如何恢復。
4. **每個使用者 agent 的任務卡**：角色 ID、情境、測試身份與權限、起始狀態、目標、步驟、禁止操作、輸入的合成資料、成功及失敗判準、期望證據、對其他 agent 的依賴。
5. **Agent 清單和模型路由表**：按 `model-routing.md` 建議主 agent、Agent 1/2/3/4、每個使用者 agent、可選 developer/reviewer 的 Pro/Flash、理由、降級條件與預算理由；對未知可用模型留空待核實。
6. **計劃與空白**：計劃覆蓋的路徑、未覆蓋風險、需要委託人確認的假設與具體問題。
7. **審批欄**：報告版本、確認／要求修訂／停止、是否可將此版本作為下階段基線。未獲明確確認不可繼續。

## 2. Agent 2 的 MCP 判定卡

每個待測步驟列：目標能力、現有 UI／自動化／測試 API／日誌能否滿足、目前缺失的操作或可觀察性、無 MCP 替代方案、最小 MCP 工具名稱與讀／寫權限、需改動的專案範圍、是否會跳過待測的真實確認、是否有合成資料和測試環境、後續維護成本。結論僅為「不需要／需要／資料不足」。需要時另列交委託人審批的 developer 範圍、reviewer 驗收條件和不建置時可測範圍。沒批准不可施工。

## 3. 事件紀錄契約

每個 agent 以相同欄位記錄：`run_id`、`journey_version`、`role_id`、`task_id`、`step_id`、`sequence`、`actor`、`action`、`channel`（UI／API／MCP）、`expected`、`observed`、`evidence_ref`、`timestamp`（實際記錄而非估算）、`data_classification`（合成，禁止真實敏感資料）、`gate_status`（可繼續／暫停／未確認）。涉及角色交接時另附 `handoff_id`、`artifact_id`、`artifact_version`、`consent_ref`、`sender_role_id`、`recipient_role_id`；讓發送、授權、接收與撤回事件共享同一交接 ID，以版本區分修訂前後的資料。缺少證據或實際系統狀態時標明「未觀察」，不得以角色的主觀聲明補上。

委託人批准關卡亦記錄為可追溯事件：附原始確認訊息或可核查的引用、被批准報告版本、確認範圍、後續啟動事件。Agent 3 在可持續監測的環境隨 Agent 1 同時啟動；否則根據關卡紀錄於每階段及事後審核，明示缺少即時監控。其檢查點包括：報告是否先給委託人審批；MCP 是否有獨立授權和 reviewer 驗收；測試角色／帳戶是否隔離；步驟是否依序；授權前接收方能否接觸資料；失敗與重跑是否留痕。

## 4. 使用者與交接分數

先固定權重再測試。使用者 agent 各給自己的任務 0–100 分：完成度 35、清晰與預期 20、內容控制與修正 25、失敗恢復 20。逐項列 `score`、具體理由、證據來源、優點、缺點、下一步建議；不適用項目須先經委託人調整權重，不應測後任意重新分配。

Agent 4 每個**測試執行有效**的交接給 0–100 分：資訊送達與權限 35、內容可理解與忠實 30、接收方可繼續工作 20、異常及撤回處理 15。逐項關聯同一 `handoff_id` 下的發送、授權、接收及狀態證據。**有效地觀察到產品交接失敗，仍是一項有效測試，對失敗維度給低分或 0；不是「無效測試」**。若接收方未曾有機會操作，標明未執行，不能擅給 0 或 100。

Agent 3 對每個測試給有效性「有效／部分有效／無效／未執行」，對部分有效寫明可用步驟範圍；只為已核對的子步驟呈現分項，**不為部分有效的整個任務輸出一個貌似完整的總分**。無效結果不得算入整體分；有嚴重授權、私隱、未成年人保護問題時單列阻斷項，不讓其他高分沖淡。多任務及多交接的整體平均權重必須在測試前由委託人確認，否則只展示逐任務及逐交接分數，不計單一產品總分。不能用模擬結果推斷真實採用率、社工專業適切性、合規或臨床效用。

## 5. 主 agent 最終匯總

列出評估日期、報告版本及審批紀錄、實際使用的模型／路由、實際執行的角色和任務、每項分數與有效性、Agent 4 交接發現、嚴重阻斷項、已證實的優點與缺點、按影響與修正成本排列的建議、仍需真人研究／專業審查的假設、來源及重跑方式。保留矛盾，不自行把不同 agent 的相反觀察捏合成一致敘述。

## 6. Unfold 的假設性例子（非執行結果）

以三個潛在使用者角色（中學生、大學生、社工）討論「本機語音記錄 → 選取記錄 → 去識別文字送雲端 → 檢視修訂摘要 → 另行批准分享 → 社工接案」。中學生與大學生的不同同意與使用環境需分開；社工只應讀到學生已批准的摘要。先對照實際產品版本是否可操作；若只是文件構想，寫「無法測試」，不可給成功分。語音與文字偏好、真人專業用途及機構接案能力仍需真人驗證。例子只供 Agent 1 初步提案，不能免去委託人審批。
