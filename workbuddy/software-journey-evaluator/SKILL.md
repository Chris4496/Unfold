# 多代理軟件旅程評估

## 定位

以可重用方法評估產品中「不同使用者能否完成任務、能否順利交接」。先作旅程分析並交委託人確認，再評估 MCP 必要性，最後在隔離環境模擬及評核。將需求主張、實際實作及真人需求驗證嚴格分開；不把代理模擬分數稱為市場、臨床或合規結論。

讀取 `references/api_reference.md` 取得報告及事件紀錄格式；在 Agent 1 為各代理配置模型前，讀取 `references/model-routing.md`。`assets/example_asset.txt` 提供純合成事件例子；`scripts/example.py` 是可選、純離線且只讀的 JSON 事件格式檢查器，須由操作者明確指定檔案，**不要自動執行或掃描目錄**。引用的 Unfold 案例只供試點參照，不把其中角色預設為其他產品的固定角色。

## 角色與職責

- **主 agent**：只與委託人交流、轉交材料、展示專職 agent 的報告、取得明確決定、按已確認規格派發工作及匯集來源與分歧。關卡與流程留痕的 timestamp 必須以實際指令（如 `date`）取得，不得估算。不自行代替 Agent 1 發現流程、代替 Agent 2 判斷 MCP，或自行修改評分。
- **Agent 1／旅程分析**：分析文件、介面及有授權的原始碼；定義參與者、步驟、例外、權限、交接與 N 個使用者 agents 的任務卡；**逐一推薦 Pro 或 Flash 模型層級並說明理由**。輸出書面分析報告，由主 agent 交委託人審閱。
- **Agent 2／MCP 必要性**：在旅程報告獲確認後檢查現有 UI、瀏覽器工具、測試 API、日誌與資料夾是否足夠；只在必要時提出最小 MCP 能力和不建置的替代方案。不得自行動手建置。
- **developer agent + reviewer agent（按需）**：僅在 Agent 2 判斷需要且委託人另外批准工程範圍時建立。前者實作隔離、最小權限的測試工具，後者獨立審查程式、權限、測試與回退；不通過便退回修正。
- **使用者 agents × N**：依已批准任務卡，以獨立角色及測試帳戶操作軟件，記錄證據、自身流程分數、優缺點與改善建議；不能靠私下代理對話假裝產品交接成功。
- **Agent 3／流程監控**：從審批關卡開始記錄執行是否有效；正式模擬時監測每個檢查點的操作與狀態，分辨產品故障、環境故障及證據不足。若缺少即時事件流，改以可驗證檢查點和事後審核，不聲稱連續即時監控。
- **Agent 4／跨角色評核**：只根據產品內發生的授權、訊息、狀態及責任交接評分。代理團隊內部任務協作屬 Agent 3 的監控範圍。

常設為主 agent + Agent 1/2/3/4，共 5 個職責；N 個使用者 agents 動態決定；只有 MCP 工程獲批准才另外啟動 2 個工程 agents。按角色分工而非為湊數固定代理數量。執行環境若不支援某種自訂代理或持久共享狀態，按相同角色契約啟動可用子代理並明示限制；不得捏造已部署的代理。

## 工作流與停止關卡

### A. 旅程報告，必須先停

1. 接收產品、目標、來源、可讀程式碼、可操作環境與預期測試範圍。先要求所需授權，不碰正式環境或真實敏感資料。由主 agent 以已可用的 Pro／高推理路由啟動第一輪 Agent 1（其建議不可能追溯改變已啟動的模型）；若可行，同步啟動 Agent 3 見證關卡。若不能持續監測，主 agent 記錄原始確認訊息、報告版本與先後順序，供 Agent 3 事後核對並註明非即時監控。
2. 派 Agent 1 產出「提案／可觀察實作／未知」對照、旅程圖、角色與交接矩陣、任務卡、必要證據、風險、各代理的 Pro/Flash 推薦與成本理由。不得將文件主張當成產品已完成的證據。
3. 由主 agent **把完整旅程分析報告展示給委託人**，詢問「確認、要求修訂，還是停止」。若需修訂，交回 Agent 1；**未收到明確確認前，不啟動 Agent 2、使用者 agents、測試或工程分支**。本輪可以報告為最終產物並等下次指示。將確認的報告版本與範圍作為後續任務唯一基線。

委託人可預先對多個關卡作概括授權。主 agent 仍須逐關卡留痕，逐關卡記錄為「概括授權通過（效力受限）」；凡以概括授權通過的關卡，其結論一律標示「待委託人事後確認，可推翻」，在委託人覆核前不得稱為正式確認。

### B. MCP 決策與可選工程

4. 確認後派 Agent 2 提供「不需要／需要／資料不足」的判斷；逐項列出已可用工具、測試盲點、所需能力、權限風險、替代方案。**不要預設要建 MCP**。
5. 若不需要，跳過工程分支；若資料不足，先補資料或降低範圍。若需要，主 agent 展示最小工程計劃及變更範圍，**再單獨取得委託人明確批准**。未批准便不可修改產品、安裝或連接 MCP；可提出有限測試方案並標明缺口。
6. 僅在獲批准後派 developer 實作；再派獨立 reviewer 驗收，查最小權限、敏感資料、測試覆蓋、失敗處理、回退與有無跳過使用者同意。審查未通過不可進入正式模擬；退回修正或改用不建 MCP 的有限方案。不得以 MCP 的內部寫入代替產品 UI 本應驗證的互動。

### C. 角色模擬、監控、交接評核

7. 準備隔離環境、合成資料、專屬測試帳戶與可追溯的事件紀錄。主 agent 按已批准任務卡與模型建議派使用者 agents；若執行環境不支援建議層級，停止靜默替換，報告實際模型／層級及影響並讓委託人選擇是否繼續。按依賴關係安排任務：獨立情境可並行，同一交接的接收方必須等發送方完成產品內狀態變化。
8. 讓使用者 agents 先走正常路徑，再走相關拒絕／修訂／取消／逾時／恢復路徑，留下操作、時間序、實際畫面或狀態、證據來源及不確定性。Agent 3 在預設檢查點核對是否照批准路徑執行，標記「有效／部分有效／無效／未執行」，必要時暫停和重跑。Agent 4 在有有效的交接證據後評核跨角色交接。
9. **C-探索階段（探索型角色扮演）**：驗證型模擬完成後才進行，先驗證型、後探索型，兩者分屬不同 agent。Agent 1 須在旅程報告新增「Persona 卡」章節（格式見 `references/api_reference.md`），作為探索型 agent 的唯一角色依據。探索型 agent 遵守隔離規則：禁讀旅程報告、程式碼、repo 文件與預期值；只使用產品 UI；以全新環境與身份操作。產出為敘事旅程日誌與摩擦點清單（迷路／誤解／預期落空），不給數字分，並標明屬代理推斷。
10. **C-圓桌階段（使用者 agents 聚集討論）**：在 Agent 4 評核之後、最終匯總之前進行。參與者為同一 persona 的驗證型與探索型使用者 agents 全部；Agent 1/2/3/4 不參加，僅可在後續引用討論內容作假設線索。形式為書面多輪 round-robin：第一輪各交「我這角色看到最重要的三個問題」，之後各讀他人備忘並回應；以 resume 原 session 延續，保留各 agent 記憶。主 agent 只做信使，遞交與收攏檔案，不主持、不評論、不總結觀點。討論紀律：反駁須引用事件 ID 或證據；無證據意見標「直覺」；矛盾並存不捏合；新點子標「未驗證假設」；討論不改變證據，只產生詮釋與假設。產出格式見 `references/api_reference.md`。
11. 按 `references/api_reference.md` 的評分規則彙總。無效結果不計分；證據不足標為待驗證。探索與圓桌產出以代理推斷與未驗證假設身份列入，不與實測證據混同。私隱、授權及未成年人保障違規是阻斷項，不以平均分抵銷。主 agent 只匯集、指明來源、列出矛盾及要求補證，不臨場替換子代理結論。產品流程或權限重大更改時，回到 Agent 1 產出新版報告並再經委託人確認。

## 模型分配規則

把 **Pro / Flash 視為預算與推理能力層級，而非特定供應商的保證型號**。首次啟動 Agent 1 前，由主 agent 按本技能的預設以可用的 Pro／`reasoning` 路由啟動；若無法指定則註明實際路由。主 agent 的現有對話模型亦不能由 Agent 1 事後更改；Agent 1 對主 agent 與自己的模型建議，僅適用下一輪會話／重跑，並需說明首次啟動的模型。Agent 1 必須在旅程報告附模型路由表，列出主 agent、Agent 1/2/3/4、每個使用者 agent、可選 developer/reviewer 的「建議層級、原因、可否降級、升級條件、實際執行時的型號／別名」。高風險授權、含糊跨角色依賴、隱私敏感交接及獨立程式審查偏向 Pro；重複、低風險、有明確成功判準的單一路徑與事件整理偏向 Flash。Agent 1 可建議模型分配，但主 agent 需在派發前檢查可用模型與執行環境是否真的支援逐代理指定；未核實不得聲稱選用成功。

若可用子代理啟動接口只提供 `reasoning`／`lite` 路由，將其作 Pro／Flash 的**操作性近似**，不宣稱對應到特定品牌或精確型號。若有已核實的確切模型 ID 才填寫並使用該 ID。若不能逐代理指定，說明改用 Auto／預設後原成本與品質假設不再保證，請委託人確認是否繼續。參閱 `references/model-routing.md` 的矩陣與升級規則。

## 安全與品質界線

只用合成案例／模擬帳戶開始；未成年人及敏感資料不作實際代理測試輸入。不可提供診斷、治療或自動風險分流；正式服務、真人感受、商業需求和法律合規另由有資格人士驗證。單憑程式碼或 MCP 可讀取內部狀態，不能取代使用者可見的端到端測試。呈交每個分數的任務、權重、可重現證據及有效性狀態；未實作功能記「無法測試」，不假設成功。
