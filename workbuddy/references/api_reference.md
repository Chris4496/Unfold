# 報告、事件與圓桌契約

以合成資料進行自然角色使用。所有產物標明來源是代碼線索、文件主張、實際介面觀察、代理自述或研究者假設；不能冒充真人回饋。

## 1. 開始前提案

Agent 1 依 [agent1-analysis.md](agent1-analysis.md) 讀項目，自行提出產品理解、**使用者 agent 人數**、逐人背景／生活處境、習慣、動機、顧慮、起始情境、開放目標、範圍及預計交接。研究問題與技術來源在研究者側，角色卡不含答案或指定路線。JSON 與呈交用戶的 Markdown 使用同一版本。

主 agent 依 [execution-approval.md](execution-approval.md) 完成最低限度準備核對，呈交逐項限制／替代操作、處理選項及結論影響。保存角色方案與執行方案兩次人類確認；可以同一次回覆，但須涵蓋兩個範圍。概括授權不能取代具體確認。無限制仍確認執行方案，未選擇或選擇暫停不能派角色。

## 2. 可選工具工程

Agent 2 只在具體 UI 操作能力不足時協助提出現有工具、替代方法或最小工程方案。MCP／產品修改不是預設前置。列改動範圍、權限、資料、被繞過的互動及驗收條件，再取得相應授權；接受現況繼續不等於授權工程。

## 3. 角色卡與事件

角色使用沒有分析歷史的新會話與獨立身份，只收到自己的卡片、公開資訊、入口，以及人類已同意的最低必要輸入替代約定。不能讀項目源碼、完整分析、研究問題、缺陷清單或預期結果。可探索、返回、迷路、求助或放棄，不能因想完成任務教角色繞過摩擦。

每項有意義的行動至少記：

- `run_id`、`journey_version`、`role_id`、`task_id`、`step_id`、`sequence`、`actor`；
- `action`（生活語言）、`intent`、`expected`、`observed`、`reaction`、`next_choice`、`evaluation`；
- `channel`（角色預設 UI；準備工作的 API／工具觀察不冒充角色行動）、`evidence_ref`；
- `timestamp`（實際取得，不估算）、`data_classification: synthetic`、`gate_status`；
- `observation_class`：`product_experience/environment_limitation/excluded_scope/agreed_substitution`，替代／排除／限制另記 `decision_ref`。

事件是簡短可讀的目標與感受自述，不要求展示內部推理。未自述的想法標研究者推斷，不補寫成事實。`evidence_ref` 可引用截圖、介面文字、操作紀錄等，缺少所需證據標未觀察；不為每個小動作強制截圖。舊 `scripts/example.py` 只檢查基礎欄位，不能驗證觀察品質或人類批准。

**文字代替話語**是 `agreed_substitution`，內容是角色自然會說出的話。可觀察輸入、儲存及後續互動，不能推論錄音、轉寫或完整語音體驗。不能安排「mic 不可用」情境或編造被迫打字的不滿。遇到新的工具阻礙保留紀錄，按確認契約停下受影響部分。

跨角色資料／責任交接另附 `handoff_id`、`artifact_id`、`artifact_version`、`consent_ref`、`sender_role_id`、`recipient_role_id`，共用 ID 連起實際發送、同意、接收、回覆或撤回。用種子示範資料觀察接收畫面時要明示，不能當作本輪學生完成分享。

## 4. 觀察品質與交接分析

Agent 3 事後檢查兩關是否得到人類確認、角色與帳戶是否隔離、回報是否有紀錄支持、替代方式是否照批准範圍使用、新限制是否留痕。不要擅自把自然使用改成固定路線驗收。

逐角色／片段標「有效／部分有效／無效／未執行」並說明範圍，評的是證據品質。自然放棄、迷路或產品交接失敗可形成有效觀察；被排除的環節是未執行。工具限制與同意的替代操作不自動算成產品摩擦，不能靠事後下調分數掩蓋受污染的感受。

Agent 4 比對同一交接的兩側：分享者理解自己交出甚麼嗎、接收者理解背景與責任嗎、能否繼續、訊息／狀態是否清楚。未發生的交接列未觀察，不給成功或零分。

預設定性評價，不算產品總分、真人滿意度或模擬採用率。用戶另要求量化時事前另確認維度與權重，只為觀察成立的範圍給分，明示是代理評價；不能套用 archive 的舊分數規則。

## 5. 圓桌

角色使用結束後，由本輪使用者原會話參與書面多輪討論；主 agent 只轉交材料，Agent 1/2/3/4 不參加。第一輪各提重要體驗與問題，後續讀其他角色觀點再回應。不能延續原會話時，按事前確認方法重建自己的記憶，明示方法限制，不假裝 resume 成功。

保留共識、爭議、未驗證假設與分角色優先級。反駁關聯事件或證據；直覺標直覺。不能把角色原先不知道的研究解答塞進記憶、改寫操作證據或捏合矛盾。

## 6. 最終報告與完成後 Dashboard

先完成角色日誌、Agent 3 審核、適用的 Agent 4 交接分析、圓桌與最終報告，再生成獨立 `test-runs/<run-id>/dashboard.html`。保留實際角色人數、背景、行動、期待、反應、評價、分歧與研究建議，以及兩關原始確認、限制處理和證據範圍。

Dashboard 沿用可讀的歷史流程頁風格，預設靜態 HTML，不要求監控 server、即時刷新或事件串流。每輪分開，資料只來自本輪完成材料，缺項顯示未觀察。主文不以 JWT、curl、API 或資料欄位敘述角色故事，技術資料置展開證據區。按相對路徑連結本輪證據，便於搬移；標「完成後整理」，不把過程紀錄稱為即時監控。
