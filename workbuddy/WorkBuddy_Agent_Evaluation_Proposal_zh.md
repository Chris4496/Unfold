# WorkBuddy 多代理軟件流程評估提案

*以 Unfold 為首個驗證案例；此文件描述擬議方法，不代表已建立 Skill、agents、MCP 或完成產品測試。*

## 1. 目標與範圍

建立一套可在不同軟件重用的 WorkBuddy 評估流程：先由 Agent 1 理解各角色的使用旅程，**提交分析報告給委託人審閱並等待確認**；再由 Agent 2 判斷是否需要 MCP 輔助測試，必要時才經批准啟動 developer agent 與 reviewer agent 建置及驗收；其後由對應的「使用者 agent」在測試環境實際走流程，記錄體驗與分數，並由 Agent 3 監控執行、Agent 4 評核跨角色交流。主 agent 只與委託人交流、按已批准的規格派發工作及匯集結果，不自行取代專職 agent 作產品分析或打分。

本方案優先回答「設計的流程是否可操作、各角色是否能完成任務、交接是否清楚、實際實現與設計有何落差」。它**不能單憑代理模擬證明市場需求、真人使用意願、臨床成效或正式服務的合規性**；這些應另以真實研究及專業審查驗證。

## 2. 代理架構

採用 **5 個常設職責 + N 個動態使用者 agents + 最多 2 個按需工程 agents**。常設職責是主 agent、Agent 1、Agent 2、Agent 3 和 Agent 4；N 由 Agent 1 按產品實際參與角色與情境決定。只有 Agent 2 判斷 MCP 確有必要、委託人批准後，才增加 developer agent 與 reviewer agent。角色可重用，但情境差異足以改變任務或權限時，應拆成不同使用者 agent。

| 角色 | 核心職責 | 主要交付 | 不負責 |
| --- | --- | --- | --- |
| 主 agent（對話及匯集） | 接收目標、轉交材料；將 Agent 1 報告和 Agent 2 建議提交委託人審閱；取得明確決定後依批准的清單派發；收集各報告並說明分歧與證據。 | 審批紀錄、統一摘要、來源連結、待確認問題。 | 自行發現角色、決定是否需要 MCP、模擬使用或臨場改寫分數。 |
| Agent 1（流程分析及角色設計） | 分析需求文件、產品介面、原始碼及可用測試資料；列出端到端流程、決策、例外、角色、權限及交接；定義使用者 agents 的職責與任務，並按任務風險為各 agent 建議 Pro／Flash 模型層級及升級條件。 | **先交委託人審閱的旅程分析報告**：旅程圖、角色清單、任務與成功條件、交接依賴、已知／未知、測試所需能力及模型路由表。 | 未經委託人確認就開始使用者模擬，或將文件構想誤判為已實作功能。 |
| Agent 2（MCP 必要性分析） | 在旅程報告獲確認後，盤點現有介面、測試工具、API、日誌與權限；判斷 MCP 是否確實提升模擬與觀測，並比較不用 MCP 的替代方案。 | 「不需要／需要／暫無法判定」建議、理由、最小工具清單、風險與工程範圍。 | 自行修改產品或在未獲批准時啟動 MCP 建置。 |
| developer agent（按需） | 僅在批准範圍內於隔離環境設計、實作與測試最小權限的 MCP 接口及必要測試適配。 | 程式變更、工具契約、測試與回退說明。 | 觸碰真實敏感資料，或用 MCP 繞過待驗證的使用者確認。 |
| reviewer agent（按需） | 與 developer 分離，審查權限、資料暴露、失敗處理、測試證據及接口是否真正支援所需流程；不通過則退回修正。 | 審查結論、缺陷與驗收證據。 | 把「程式可啟動」當作安全及流程已獲驗證。 |
| 使用者 agents（動態建立，N 個） | 各自以指定身份、資料和權限模擬完整任務，記錄操作、結果及感受；按共同評分規則對自己的使用流程給分，列出優點、缺點和改進建議。 | 個別角色任務紀錄、分數、問題清單及可重現證據。 | 直接越過產品介面互相交換結果，以假定交接成功。 |
| Agent 3（執行監控） | 全程比對已批准流程與實際執行，檢查是否跳步、卡住、超權、只作口頭模擬或缺少證據；必要時標記重跑、無效或暫停。 | 執行有效性紀錄、偏差、阻塞與覆蓋缺口。 | 取代使用者的體驗分，或把產品問題與測試環境故障混為一談。 |
| Agent 4（跨角色交流評核） | 觀察各使用者 agents **透過軟件**完成的訊息、授權、狀態與責任交接；評核資訊是否到達、被理解、可繼續處理，及異常時能否恢復。 | 交接紀錄、跨角色分數、斷點與改善建議。 | 只根據代理彼此的文字對話認定產品內的交接成功。 |

> Agent 1 先產生角色清單與任務規格，並提交報告；**委託人確認前不建立或啟動使用者 agents**。如 WorkBuddy 的實際執行環境要求由主 agent 發起子代理，主 agent 只按已批准規格機械式啟動，不自行重新設計角色。具體編排能力需要在實作時核對。

## 3. 一次評估的完整流程

### 階段 A：旅程分析、書面報告與第一個審批關卡

1. 委託人提供目標產品、評估範圍、需求文件、測試環境及可選的原始碼。主 agent 轉交材料；Agent 3 自此記錄各階段是否依序完成及是否越過審批關卡。
2. Agent 1 建立「聲稱流程／已實作流程／未知」對照；識別角色、主路徑、取消與失敗路徑、資料流、權限及交接點。
3. Agent 1 **先撰寫旅程分析報告交由主 agent 提交委託人**。報告包含流程圖、角色清單、每個使用者 agent 的功能與任務卡、任務依賴、成功條件、缺漏與假設，並逐一建議主 agent、Agent 1／2／3／4、動態使用者 agents 及按需工程 agents 的 Pro／Flash 層級、理由、升級條件與成本取捨。任務卡至少包含角色與權限、起始狀態、目標、允許操作、成功條件、輸入資料及禁止事項。Pro／Flash 是策略層級，不等於已選定實際模型 ID；Agent 1 與主 agent 已啟動的模型無法由報告事後更改，啟動子代理前須核實是否支援逐代理指定。
4. **等待委託人明確確認或提出修訂**：若需修訂，交回 Agent 1 更新報告；若未確認，停止於分析階段。此時不得啟動使用者模擬，也不得因 Agent 1 建議而直接修改程式碼。

### 階段 B：Agent 2 評估 MCP 必要性

5. 旅程報告獲確認後，Agent 2 按每個待測步驟檢查現有介面、瀏覽器操作、測試 API、資料夾及日誌能否支援可觀察、可重現的測試；只在現有方法不足時提出 MCP。報告需寫明無 MCP 替代方案、所需工具與權限、可獲得的額外證據、資料風險、成本及不建置時的測試缺口。
6. 若結論為「不需要 MCP」，記錄理由並跳過工程分支；若為「暫無法判定」，先補資料或標明測試限制；若為「需要 MCP」，主 agent **向委託人提交建置建議及變更範圍，取得明確批准後**才可進入工程分支。不同意建置時，不得私自實作；可改以有限範圍測試並明示缺口。

### 階段 C：按需建置與驗收 MCP

7. 僅在批准後，由 developer agent 在隔離測試環境實作最小權限 MCP：先定義工具契約、授權範圍、合成資料及禁止操作，再編寫工具與自動化測試。原則上不連接正式環境、不讀取真實敏感資料，不用後門接口取代使用者在介面上的同意或確認。
8. reviewer agent 獨立審查程式變更、權限與資料暴露、失敗處理、測試結果及回退方式；未通過則退回 developer 修正。只有通過驗收且委託人知悉可用工具範圍，才進入正式模擬；若無法安全驗收，標記受阻並回到有限範圍方案。Agent 3 記錄審批、開發與驗收是否依序執行。

### 階段 D：角色模擬與即時監控

9. 建立隔離測試環境、合成資料及角色帳戶。主 agent 依已確認的 Agent 1 清單啟動 N 個使用者 agents；Agent 3 持續監控。互不依賴的角色情境可並行；有交接依賴的步驟須等待前置狀態完成。
10. 每個使用者 agent 以自身角色操作產品，先走正常路徑，再走與該角色相關的拒絕、修正、逾時、取消或失敗路徑；留下時間順序、操作、可見結果、系統狀態及證據。各自評分並列出優缺點；未實作的步驟標為「無法測試」，不得假裝操作成功。
11. Agent 3 比對已批准任務卡與實際事件：確認步驟是否執行、角色權限是否正確、關鍵證據是否存在；區分「產品流程失敗」與「測試本身無效／環境故障」，必要時暫停或要求重跑。

### 階段 E：跨角色評核與匯總

12. Agent 4 按交接事件檢查發送者、接收者、分享範圍、內容忠實度、狀態同步、等待及例外處理；評核不同角色透過產品交流是否順暢。
13. 主 agent 匯集使用者分數、Agent 3 的有效性判斷及 Agent 4 的交接分數，呈交可追溯的優點、缺點、問題優先次序和待真人驗證的假設。若報告互相矛盾，保留分歧並請相應 agent 補證，而不是由主 agent 私自選擇一個答案。
14. 修正產品後，按同一任務卡重跑受影響流程，記錄修正前後差異；若修正改變旅程或權限，回到 Agent 1 報告與審批關卡。

## 4. 評分與證據規則（初稿）

每個使用者 agent 對自己的任務給出 **0–100 分**，初步按任務完成 35、理解與可預期性 20、內容控制與修正 25、失敗後恢復 20 加權；每項必須附可觀察證據和一句扣分理由。產品不同時，權重應在測試前調整，不得看完結果後反向修改。分數之外，列出「最有幫助的設計」「阻礙最大之處」及具體改善方式。

Agent 4 另就每個跨角色交接給出 **0–100 分**：資訊送達與權限 35、內容可理解與忠實 30、接收方能否繼續任務 20、異常與撤回處理 15。這是交接分，不應併入某個使用者的個人感受。

Agent 3 不給產品體驗分，而是給每項測試一個有效性狀態：**有效／部分有效／無效／未執行**，並說明原因。無效結果不能納入整體數字；樣本不足時顯示「證據不足」，不強湊一個漂亮總分。若日後需要總分，可預先約定「有效的角色任務分數按關鍵旅程權重匯總，再結合交接分」，但同時必須保留各分項與嚴重問題。

涉及私隱、授權、未成年人保障或敏感內容洩漏的關鍵違規須**獨立列為阻斷項**，不能以其他項目的高分抵銷。代理模擬所得分數衡量的是原型／流程表現，並非整體商業或臨床可行性的證明。

## 5. Unfold 作為首個示例

根據《[項目提案](Project_Proposal_zh.md)》與《[中期進度報告](Interim_Progress_Report_zh.md)》，Unfold 目前描述的是待驗證的私人語音記錄、去識別化摘要、學生批准分享及社工接案流程；文件並未證明原型與真實用戶研究已完成。因此，首輪須先核實可操作範圍，再決定可實跑的任務。

**Agent 1 的初步角色清單（須再核對實際產品）：**

| 使用者 agent | 主要情境與任務 | 重要交接 |
| --- | --- | --- |
| 中學生 | 在私隱和學校支援條件下記錄、選取、檢視及決定是否分享；觀察不方便錄音及同意說明等情境。 | 資料傳送與分享授權；具體未成年人同意安排仍待專業及機構確認。 |
| 大學生 | 自主記錄多次經歷、檢查摘要是否誇大、修正與排除不願披露內容，再決定是否分享。 | 學生確認的摘要進入社工佇列。 |
| 社工（模擬帳戶） | 在已授權範圍內查看摘要、判斷是否足以開始初步對話、模擬接案與回覆。 | 接案／等待／退出／重新配對／撤回後可見內容。 |

若這三個角色均獨立建立，首輪在**不建置 MCP** 的情況下共 **8 個 agents = 5 個常設職責 + 3 個使用者 agents**；如需 MCP 且獲批准建置，另加 developer 與 reviewer，合共 **10 個**。如實際產品還有機構管理員、輔導員或其他角色，Agent 1 應在旅程分析報告中提出並待委託人確認；不預先固定使用者 agents 總數。

**首輪關鍵案例：**

- 學生記錄與選取合成經歷；核對原始錄音、完整謄本及去識別文字的預期存放位置與實際行為。
- 學生確認「送去識別文字到雲端」後生成草擬摘要；在**未批准社工分享**時，社工佇列不得看到摘要。這兩次確認不可混為一談。
- 摘要包含預設的過度描述或時間線偏差時，學生能否發現、修正並移除不願分享的家庭事件；Agent 4 核對社工最終看到的版本是否正確。
- 學生批准分享後，社工能否接案並作人工回覆；未接案、拒絕、重新配對或撤回時，雙方能否理解後續狀態。
- 已傳送雲端的資料或已被社工讀取的內容，在撤回時不得被錯誤描述為「從未離開裝置」或保證可完全刪除。

**保障界線：**首輪僅用合成案例與模擬帳戶，不收集真實學生的敏感經歷；使用者 agents 不進行診斷、治療、危機監察或自動轉介。社工 agent 只模擬產品流程，不能代替合資格專業人士評估摘要的臨床適切性。正式試行前另需釐清未成年人同意、資料保存、專業人手及緊急情況安排。

## 6. 可重用實作形式

- **Skill（可重用規則）**：保存 Agent 1 旅程報告模板與確認關卡、Agent 2 的 MCP 必要性判準、任務卡、證據格式、Agent 3 監控準則、Agent 4 跨角色評核及報告格式；換一個產品時重用方法而非照搬 Unfold 角色。
- **動態代理編排**：Agent 1 先提交角色與依賴報告，經委託人確認後才進入 Agent 2 評估；若 MCP 確有必要，只有獲批准才啟動 developer／reviewer 工程分支；完成相關關卡後，執行環境再依清單建立／啟動使用者 agents。Agent 3 記錄關卡與模擬的執行狀態，Agent 4 根據跨角色事件評核。具體 WorkBuddy 子代理啟動與共享狀態機制需在實作前驗證。
- **可選工具層**：Agent 2 優先盤點已有測試介面、日誌和 API；必要且獲批准時，才由 developer／reviewer 在隔離環境建立並驗收最小權限 MCP，用於建立合成資料、讀取可觀察狀態與執行受控操作。工具能力不得使測試跳過實際用戶必須經歷的確認與授權。

建議先由 Agent 1 就一條完整的學生至社工交接路徑提交旅程報告供審閱；獲確認後才走 MCP 必要性判斷及小型試驗，驗證真實操作證據、即時監控和跨角色評核能否協同運作，再擴展例外情境及其他軟件。

## 7. 尚待確認的設計決定

1. Agent 4 的「交流」以**產品內不同使用者的資訊／權限／任務交接**為核心；代理之間的測試任務協作主要由 Agent 3 監控。若委託人希望 Agent 4 同時評估代理團隊內部協作，需另定評分範圍，避免混為一項。
2. Agent 1 的旅程報告須由委託人確認；其後 Agent 2 判斷 MCP 是否必要。若建議建置，須另確認可修改的程式碼範圍、測試環境、最小權限、驗收與回退方式，才可啟動 developer／reviewer。
3. Unfold 是否已有可運行的原型、測試帳戶及足夠的介面／日誌？如沒有，第一輪只能交付「流程設計評估 + 可執行測試規格」，不能聲稱已完成端到端操作，也不能僅為了產生分數而建置 MCP。
4. 各角色、各交接的權重與阻斷條件，應在首輪測試前由委託人確認並固定。
