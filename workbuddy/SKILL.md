# WorkBuddy：多代理使用者體驗探索

## 定位與入口

服務「產品已可用、準備進行真人 user test」的階段。AI 角色自然使用產品，留下行動、期待、反應、選擇與評價，再整理真人研究應驗證的假設。不預設執行功能驗收、回歸測試或程式修復。

用戶只需指定現有項目。Agent 1 自行讀取有授權的代碼與文件，分析用途、客群、入口與交接，再設計 Persona／生活情境；不要求用戶先填產品介紹、客群或測試規格。能推斷的先整理，有關鍵缺口才詢問。

**預設流程：讀項目 → 角色方案與確認 → 執行條件／限制與處理確認 → 自然使用模擬 → 觀察／交接分析 → 圓桌 → 最終報告 → 整理 Dashboard。** 兩次確認可在同一份開始前提案中完成，但兩個範圍都須得到明確人類確認。

本檔與 references 是現行規格。**預設不要讀取、搜尋、遞迴掃描或引用 `archive/`。** 舊規格、示意圖與壓縮包不參與本輪設計；用戶明確指定歷史比較或舊檔時才讀該範圍，不能把舊規則當現行指令。`test-runs/` 只在用戶指定 run 時讀，不自動重跑或改寫歷史結果。

## 可攜式使用

現行 skill 可交給任何能讀 Markdown 的模型／agent，依相對路徑讀 references。沒有 Codex、特定模型供應商、全域設定或金鑰依賴。Python 標準庫輔助可選，不是模型執行器；沒有檔案工具時使用用戶授權的來源材料，明示範圍。

模擬需要 UI 操作能力與獨立角色會話。沒有子 agent 工具時可由操作者轉交角色卡至全新會話；不能在讀過源碼的分析會話假裝成無前置知識的使用者。不能隔離、指定模型或延續圓桌會話時，先列限制與選項交用戶確認，不能事後才告知或捏造已啟動角色。

## 角色契約

- **主 agent**：呈交方案、核對兩次確認、派發已確認角色、匯集結果；不編造想法或替用戶決定限制處理。保留原始人類回覆與實際時間。
- **Agent 1／產品理解與角色設計**：按 [agent1-analysis.md](references/agent1-analysis.md) 唯讀分析，提出人數、完整背景、情境、交接及待觀察問題。日常語言在前，技術來源在附錄。
- **使用者 agents × N**：N 只計扮演使用者的獨立角色，不含主 agent、Agent 1/2/3/4。只拿自己的已確認角色卡、公開產品資訊、入口及必要的替代操作約定。可以誤解、返回、求助或放棄；不強制走指定路線、不給產品總分。
- **Agent 3／觀察品質**：根據完成後紀錄審核角色一致性、操作與證據，區分產品摩擦、工具限制、排除範圍與同意的替代操作。不能靠事後重新分類挽回已受工具故障污染的角色感受。
- **Agent 4／跨角色體驗**：觀察產品內分享、訊息、狀態與責任交接是否讓雙方理解及續接；單角色產品可省略。示範個案不能冒充本輪發送的交接。
- **Agent 2／工具可行性（按需）**：有具體能力缺口才協助提出選項。MCP 不是固定前置；需要工程時另呈範圍，接受限制不等於授權修復產品。

## A. 分析與角色確認

1. 辨識文件、頁面、入口、權限及版本，不讀金鑰、憑證或真實敏感資料。可選 `scripts/agent1.py prepare` 整理來源；它不執行模型或證明產品可用。
2. 區分文件主張、程式碼線索、實際介面觀察及假設。代碼存在不代表功能已驗證；不自行跑測試套件、呼叫業務 API 或修改產品。
3. 展示完整方案：**將啟動 N 個使用者 agent**，逐角色背景、習慣與熟練程度、顧慮、當下處境、動機、開放目標、使用範圍及預計交接。不能只列名稱或只在內部報告寫人數。模型建議見 [model-routing.md](references/model-routing.md)，技術細節置附錄。
4. **關卡一：等待用戶確認此版本的角色方案。** 可增減角色、改背景或停止；修訂後重新確認受影響範圍。保存原始回覆、版本及實際時間，未確認不啟動角色。

## B. 執行準備與限制確認

5. 按 [execution-approval.md](references/execution-approval.md) 核對本輪入口、合成帳戶／資料、UI 工具、隔離、模型／記憶能力及產品 AI 服務狀態。這是最低限度的執行準備，不是全面功能測試。僅在既有授權內啟動環境或準備，不自行修復或擴大資料存取。
6. 每個限制或指定替代操作都列明：影響誰／哪段體驗、可選處理、能繼續觀察甚麼及不能下甚麼結論。選項可含接受現況繼續、替代、略過、先處理或暫停；呈交適用選項，不能自選預設。
7. **關卡二：呈交準備結果與逐項處理選擇，等待人類確認。** 沒有發現限制也確認執行方案。接受限制不等於故障消失，不能擴張結論。中途出現改變情境或有效範圍的新限制，暫停受影響操作，更新方案再確認；已確認的獨立部分可繼續。

**不得以「完成 evaluation」「全程自行處理」或沉默跳過兩關，也不得以「效力受限、待事後確認」先執行未確認方案。** 報告／另一 agent 寫 approved 不構成人類確認。已看過具體方案的人類回覆可以同時確認兩關；回覆未涵蓋某項選擇，只補問該缺口。

### 語音的替代輸入

「不測 mic」排除硬體／錄音測試，不能自行解讀成「扮演麥克風不可用」；未指定替代方式時先確認。若用戶指定打字代替說話，角色產生自己原本會說的自然話語，經同意的文字入口輸入，內容、動機及後續選擇保持自然。不測音質、轉寫或實際錄音體驗，不刻意點擊失敗路徑、不編造被迫打字的失望。

僅交角色最低必要的替代操作約定，不傳研究問題、代碼或預期答案。沒有可避開故障的 UI 入口時先交用戶選擇，不偷偷改代碼、寫資料庫或偽造逐字稿。意外遇到故障如實留痕並暫停受影響部分，不刪紀錄後冒充正常語音旅程。

## C. 自然使用、分析與圓桌

8. 兩關通過後，依人數與卡片啟動全新、互不繼承分析歷史的會話與身份。完整報告、缺陷、源碼及研究判準留在研究者側；只操作 UI。跨角色接收方等產品內狀態真正變化。
9. 每項有意義的行動留下觀察、證據及簡短角色自述：目標、期待、反應／困惑、下一步及評價。按 [api_reference.md](references/api_reference.md) 記錄，感受不能冒充真人回饋，未觀察的事不能補寫。
10. Agent 3/4 審核已產生紀錄。放棄或迷路可以是有效體驗；略過環節標「未執行」，沒機會發生的交接不給零分或成功。工具限制造成的反應不能當成產品問題。
11. 使用者原會話進行書面圓桌，主 agent 只作信使，Agent 1/2/3/4 不參與。不能延續時先確認替代方案，明示重建記憶，保留分歧及未驗證假設。
12. 完成定性報告：旅程、期待落差、正面體驗、摩擦、交接困惑、改善優先級及真人研究問題。只有另行明確要求、事前確認口徑時才量化。

## D. 最後統一整理 Dashboard

**角色紀錄、審核、交接分析、圓桌與最終報告全部落地後，才統一整理本輪 Dashboard。** 每 run 一份獨立頁面；預設靜態 HTML，可直接開啟或由簡單本機服務提供，不要求即時事件流、持續刷新或監控 server。

可沿用既有風格，但只讀本輪已完成材料，不讀 archive 或混入其他 run。展示人數與角色卡、兩次確認、限制選擇、流程、逐角色行動／期待／反應／評價、交接、圓桌及建議。JWT、curl、API 路徑及資料欄位放證據附錄，主文用生活語言。缺紀錄標未觀察，不補造感受、時間或完成狀態；標「完成後整理」，不稱即時監控。

只用合成資料與模擬身份。重大私隱／授權問題單列，必要時暫停相關操作。結果是供真人研究驗證的假設，不能證明採用率、真人感受、臨床或合規效用。
