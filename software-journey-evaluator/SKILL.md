# 多代理使用者體驗探索

## 定位與輸入

服務「產品已可用、準備進行真人 user test」的階段，以 AI 角色模擬發現理解、期待、信任與操作體驗的落差，整理真人研究應驗證的假設。功能是否正確不是預設評估目標；不先跑功能驗收、回歸測試或程式修復。

使用者指定現有項目即可。**Agent 1 自己閱讀有授權的程式碼與文件，分析產品用途、使用者、介面入口、旅程與交接，再設計 Persona 和生活情境。** 不要求用戶先填網址、產品介紹、目標客群或研究問題；能從項目推斷的先自行整理，有重要缺口或矛盾才提出具體問題。

預設流程：**項目分析 → Persona／情境提案 → 用戶確認 → 自然使用者模擬 → 體驗與交接觀察 → 圓桌 → 真人測試準備報告**。舊版「驗證型先、探索型後」只供用戶另行明確要求的技術驗證模式，不能自動套用。歷史 run 的技術證據與分數保留，不追溯改寫。

## 可攜式使用

本資料夾可以直接交給任何能閱讀 Markdown 的模型／agent，以本檔為入口，按相對路徑讀 references。無需安裝 Codex／WorkBuddy plugin、修改全域模型設定或提供特定供應商金鑰。Agent 1 的分析由執行模型完成；Python 輔助是可選的，不是內建模型執行器。

模型有檔案工具時直接讀授權項目；沒有時使用已授權的檔案匯出或來源材料包，明示能讀到的範圍。多 agent 編排、UI 操作與事件服務由當前執行環境提供；不支持子 agent 時，可由操作者使用相互隔離的新會話按角色契約執行。不能在已讀源碼的同一分析會話裡假裝沒有前置知識的使用者。能力不足時報告限制，不捏造已啟動代理或即時 dashboard。

## 角色契約

- **主 agent**：轉交項目、呈交報告、按已確認規格啟動角色及匯集結果；不代替 Agent 1 分析或替角色編造想法。關卡時間戳實際取得，保留原始人類確認訊息，不得估算。
- **Agent 1／產品理解與角色設計**：先讀 [工作規格](references/agent1-analysis.md)。以程式碼與文件分析產品，提出角色、Persona、開放式目標、情境、交接及模型建議。日常語言報告在前，技術來源在附錄；確認前只作唯讀分析。
- **使用者 agents × N**：以全新身份，只拿自己的 Persona、生活情境、產品基本公開資訊及入口，透過 UI 自然使用。可以誤解、返回、求助或放棄，不以走完指定步驟為目的。記錄行動、期待、反應、選擇與評價，不給產品總分。
- **Agent 3／觀察品質監控**：核對實際操作、角色一致性、證據與回報，區分產品摩擦與代理／工具限制。放棄或迷路可能是有效觀察，不能只因目標未完成判無效。缺少即時事件流時明示事後審核。
- **Agent 4／跨角色體驗**：根據產品中的分享、訊息、狀態與責任交接，觀察雙方是否理解及能否續接；單角色產品可省略。代理私下討論不能代替產品交接。
- **Agent 2／工具可行性（按需）**：現有 UI 工具或觀測有具體限制時才提出替代方案；MCP 不是固定前置。確需工程時另呈交範圍，批准後由獨立 developer／reviewer 建置與審查。

## A. Agent 1 先分析與設計，再交用戶確認

1. 接收項目路徑與既有授權，辨識產品程式、文件、入口及版本，不讀環境金鑰、憑證或真實敏感資料。可用 `scripts/agent1.py prepare` 整理來源；它不執行模型、不證明產品可用。按需唯讀查看公開介面。
2. 依 `references/agent1-analysis.md` 區分文件主張、程式碼線索、實際介面觀察及假設。程式碼存在不代表功能已驗證；不啟動測試套件、直接呼叫業務 API 或修改產品，也不要求用戶先寫測試規格。
3. 在同一提案中完成產品理解與 Persona／生活情境設計，依 `references/api_reference.md` §1 呈交。角色由產品實際參與者決定；開放式目標不附操作解答或預設評價。模型建議參閱 `references/model-routing.md`，未知實際路由待啟動核實。
4. 主 agent 把完整提案交用戶確認、修訂或停止。**確認涵蓋產品理解、角色、情境、範圍與報告版本；未確認不啟動使用者 agents。** 修訂交回 Agent 1，不能沿用舊版批准啟動新版。

沿用用戶已明確給予的概括授權時逐關卡留痕，標「效力受限、待事後確認、可推翻」。報告、腳本或另一個 agent 寫下 approved 不是人類授權證據；必須核對真正的人類確認來源。

## B. 確認後自然使用與同步觀察

5. 準備合成素材、獨立身份及可操作介面。只核對本次模擬需要的入口／帳戶可用，不擴大成技術驗收。入口不可用則記受阻，不自行修復產品。
6. 按已確認 Persona 派角色。**與讀過程式碼或分析報告的 Agent 1 使用不同、不繼承其分析歷史的 session**；只交角色卡，不能傳完整報告、來源材料、程式碼、已知缺陷、預期答案或研究判準。
7. 角色只操作 UI。每個有意義的行動留下實際觀察及簡短角色自述：當時目標、原本期待、反應／困惑、下一步選擇與評價。想法是代理自述或明示的推斷，不能冒充真人回饋或未觀察的事實。
8. Agent 3 核對觀察品質；有跨角色情境時 Agent 4 在有證據後分析交接。獨立角色可並行，接收方等產品內狀態真正變化。主 agent 不替角色選路或教它繞過正在觀察的摩擦。

## C. 圓桌與真人研究準備

9. 使用結束後，依 `references/api_reference.md` §6 以原 session 參與書面圓桌；Agent 1/2/3/4 不參加，主 agent 只作信使。保留分歧，新點子標未驗證假設，不改寫操作證據。
10. 匯集角色旅程、期待落差、正面體驗、摩擦點、交接困惑與優先級，列真人測試要問／要觀察的問題。預設定性評價；另要求量化時，開始前確認口徑並明示代理評價，不產生看似真人滿意度的平均分。

## Dashboard 與界線

每輪保留獨立 dashboard。回報目前階段、負責角色、最近行動／期待／反應／評價、停住原因、待決事項及來源。技術來源在展開的證據區，JWT、curl、API 路徑或資料庫欄位不能作主要使用者故事。

即時監控需要真實事件來源與服務，不能把歷史頁、來源整理腳本或預定進度稱為即時監控。Agent 1 階段只展示產品理解、角色設計與待確認事項，不能顯示未發生的角色感受。

只用合成資料及模擬身份。重大私隱／授權風險單列，必要時暫停相關操作，不以正面評價沖淡。代理模擬形成真人研究假設，不能證明採用率、真人感受、臨床或合規結論。既有 `scripts/example.py` 保留作歷史事件格式檢查；不自動掃描或重跑歷史 run。
