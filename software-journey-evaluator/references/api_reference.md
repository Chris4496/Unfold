# 任務契約、報告與評分格式

本檔是純文字工作模板；每次評估另產報告，不在技能檔內存放私人資料。所有結論須注明來源：需求主張、程式碼線索、實際 UI／API 觀察、合成測試事件，或真人反饋（如有）。

## 1. Agent 1 的分析與角色提案（待用戶確認）

詳細規格與 JSON 格式見 [agent1-analysis.md](agent1-analysis.md)。Agent 1 自己讀有授權的程式碼與文件，不要求用戶先填產品介紹、客群或研究問題。先分析，再設計角色／情境，兩者完成後一併交用戶確認。

1. **產品理解與分析邊界**：用途、可見功能、版本、來源及未知；區分文件主張、程式碼線索與實際介面觀察，不宣稱功能已驗證。
2. **旅程概覽與角色交接**：用生活語言描述角色想做甚麼、可能的決定、內容／責任如何交給其他人。技術來源置於附錄。
3. **Persona／生活情境**：每個角色的背景、熟練程度、隱私態度、合成素材、起始情境、一般產品資訊與開放式目標。這是給角色的獨立卡片，不含操作步驟、程式碼、已知缺陷或預期答案。
4. **研究者待觀察點、假設與限制**：由分析推導，交用戶審閱；不派給使用者 agent 作演出指令。
5. **編排與模型建議**：角色依賴、可用入口與身份準備限制、需要的觀測能力、計劃啟動代理的模型建議與成本。技術細節另列，不要求用戶懂型號或 API。
6. **確認欄**：產品理解、角色、情境、範圍與報告版本；確認／修訂／停止。先交完整提案，再取得用戶確認；未確認不啟動角色。

確認後只交付角色卡給未繼承分析歷史的新 session；完整分析報告、研究問題、源碼與預期結果留在研究者側。來源整理／結構檢查不是分析完成、功能通過或人類批准。

## 2. 按需工具可行性／MCP 判定卡

只在角色 UI 操作或觀測有具體限制時使用；不作預設前置、不進行產品功能驗收。每個受限情境列：目標能力、現有 UI／自動化／測試 API／日誌能否滿足、目前缺失的操作或可觀察性、無 MCP 替代方案、最小 MCP 工具名稱與讀／寫權限、需改動的專案範圍、是否會跳過待測的真實確認、是否有合成資料和測試環境、後續維護成本。結論僅為「不需要／需要／資料不足」。需要時另列交委託人審批的 developer 範圍、reviewer 驗收條件和不建置時可測範圍。沒批准不可施工。

## 3. 事件紀錄契約

預設體驗事件以 UI 操作為主；`action` 用日常語言記行動，`expected` 是角色當時的期待，`observed` 是實際看到的結果。另附 `intent`（目標）、`reaction`（感受／困惑）、`next_choice`（下一步選擇）、`evaluation`（簡短評價）；不要求展示內部推理。角色未自述的想法標為推斷，不補寫成事實。技術引用放 `evidence_ref` 或展開附錄，不能原樣作 dashboard 主標題。以下基礎欄位仍相容歷史事件；API／MCP 觀察不冒充角色 UI 行動。

每個 agent 以相同欄位記錄：`run_id`、`journey_version`、`role_id`、`task_id`、`step_id`、`sequence`、`actor`、`action`、`channel`（UI／API／MCP）、`expected`、`observed`、`evidence_ref`、`timestamp`（實際記錄而非估算）、`data_classification`（合成，禁止真實敏感資料）、`gate_status`（可繼續／暫停／未確認）。凡跨角色或跨程序的資料流動皆另附 `handoff_id`、`artifact_id`、`artifact_version`、`consent_ref`、`sender_role_id`、`recipient_role_id`，包括單向流動（如同步上雲、衍生產物回送），不限於雙向交接；讓發送、授權、接收與撤回事件共享同一交接 ID，以版本區分修訂前後的資料。使用者繞道時另附可選欄位 `workaround: true` 與 `workaround_reason`（原路徑受阻原因）。缺少證據或實際系統狀態時標明「未觀察」，不得以角色的主觀聲明補上。

委託人批准關卡亦記錄為可追溯事件：附原始確認訊息或可核查的引用、被批准報告版本、確認範圍、後續啟動事件。Agent 3 在可持續監測的環境隨 Agent 1 同時啟動；否則根據關卡紀錄於每階段及事後審核，明示缺少即時監控。其檢查點包括：報告是否先給委託人審批；MCP 是否有獨立授權和 reviewer 驗收；測試角色／帳戶是否隔離；步驟是否依序；授權前接收方能否接觸資料；失敗與重跑是否留痕；預設核對 Persona／目標與實際旅程、角色回報與證據是否一致，不把自然探索改成固定步驟驗收。只有另要求驗證模式才逐任務卡步驟核對事件覆蓋與完成申報，防止漏做誤報。

## 4. 定性體驗評價與可選分數

預設流程不量化角色滿意度、不產出產品總分；整理行動、期待、反應、評價與證據，逐條標「代理模擬回饋，待真人研究」。有效性是證據品質，不是角色是否走完目標；放棄、迷路或求助可以是有效體驗。以下數字規則只用於用戶明確另要求的驗證／量化模式及歷史報告，不強制自然 roleplay 照任務步驟演出。

先固定權重再測試。使用者 agent 的自評分為兩類：

(a) **執行品質分**：按現行四維度給自己的任務 0–100 分：完成度 35、清晰與預期 20、內容控制與修正 25、失敗恢復 20。逐項列 `score`、具體理由、證據來源、優點、缺點、下一步建議；不適用項目須先經委託人調整權重，不應測後任意重新分配。以繞道（`workaround`）完成的路徑，成功判準降級為「部分達成」，評分時如實反映，不得視為原路徑通過。

(b) **使用者體驗推斷**：不給數字分，只列推斷要點，逐條標明「代理推斷，非真人 UX 證據」。

Agent 4 每個**測試執行有效**的交接給 0–100 分：資訊送達與權限 35、內容可理解與忠實 30、接收方可繼續工作 20、異常及撤回處理 15。逐項關聯同一 `handoff_id` 下的發送、授權、接收及狀態證據。**有效地觀察到產品交接失敗，仍是一項有效測試，對失敗維度給低分或 0；不是「無效測試」**。若接收方未曾有機會操作，標明未執行，不能擅給 0 或 100。

Agent 3 對每個測試給有效性「有效／部分有效／無效／未執行」，對部分有效寫明可用步驟範圍；只為已核對的子步驟呈現分項，**不為部分有效的整個任務輸出一個貌似完整的總分**。無效結果不得算入整體分；有嚴重授權、私隱、未成年人保護問題時單列阻斷項，不讓其他高分沖淡。多任務及多交接的整體平均權重必須在測試前由委託人確認，否則只展示逐任務及逐交接分數，不計單一產品總分。不能用模擬結果推斷真實採用率、社工專業適切性、合規或臨床效用。

## 5. C-探索階段：Persona 卡與探索型角色扮演

預設流程在 Agent 1 的分析與 Persona／情境提案獲確認後，直接進行自然角色扮演，沒有技術驗證前置。只有用戶另要求驗證模式時才分開使用驗證型與探索型 agents。

**Persona 卡**（Agent 1 為每個探索型角色撰寫一張，列入旅程報告）：

- **背景故事**：角色身份、生活情境與使用動機。
- **科技熟練度**：對同類軟件的熟悉程度與操作習慣。
- **隱私在意度**：對資料收集、分享與留痕的敏感程度。
- **日記素材種子**：角色可能帶入使用情境的合成素材方向。
- **知識邊界**：僅產品基本使用資訊與功能，不含程式碼、報告、預期值。
- **開放式目標**：角色想達成的事，只寫目標，不含步驟。

**探索型 agent 隔離規則**：禁讀旅程報告、程式碼、repo 文件與預期值；只使用產品 UI；以全新環境與全新身份操作；不能與讀過程式碼或分析報告的 Agent 1 共用分析歷史；若另有驗證型 agent，亦分開。

**產出**：敘事旅程日誌與摩擦點清單（迷路／誤解／預期落空）。不給數字分，逐條標明「代理推斷，非真人 UX 證據」。

## 6. C-圓桌階段：使用者 agents 聚集討論

位置在 Agent 4 評核之後、最終匯總之前。預設參與者為本輪自然 roleplay 的使用者 agents；若用戶另要求驗證型，其產物保持獨立，不能在探索之前揭露答案；Agent 1/2/3/4 不參加，僅可在後續引用討論內容作假設線索。

**形式**：書面多輪 round-robin。第一輪各交「我這角色看到最重要的三個問題」；之後各讀他人備忘並回應。以 resume 原 session 延續，保留各 agent 記憶。主 agent 只做信使，遞交與收攏檔案，不主持、不評論、不總結觀點。

**紀律**：反駁須引用事件 ID 或證據；無證據的意見標「直覺」；矛盾並存，不捏合；新點子標「未驗證假設」；討論不改變證據，只產生詮釋與假設。

**產出格式**：

1. **共識發現**：有事件或證據支持、獲參與角色認同的發現。
2. **爭議並存**：未化解的分歧，並列雙方立場，不捏合。
3. **未驗證假設**：討論產生的新詮釋或新點子，待驗證。
4. **分角色優先級投票**：各角色對發現與假設的優先順序。

## 7. 主 agent 最終匯總

預設報告聚焦角色旅程、期待落差、正面體驗、摩擦點、交接困惑、分歧、改善優先級及真人測試應問／觀察的問題。歷史量化結果或另行要求的驗證須清楚標示。列出評估日期、報告版本及審批紀錄、實際使用的模型／路由、實際執行的角色和任務、每項分數與有效性、Agent 4 交接發現、探索階段的敘事旅程日誌與摩擦點清單、圓桌階段的共識發現／爭議並存／未驗證假設／分角色優先級投票、嚴重阻斷項、已證實的優點與缺點、按影響與修正成本排列的建議、仍需真人研究／專業審查的假設、來源及重跑方式。探索與圓桌產出屬代理推斷與未驗證假設，與實測證據分列。保留矛盾，不自行把不同 agent 的相反觀察捏合成一致敘述。

## 8. Unfold 的假設性例子（非執行結果）

以三個潛在使用者角色（中學生、大學生、社工）討論「本機語音記錄 → 選取記錄 → 去識別文字送雲端 → 檢視修訂摘要 → 另行批准分享 → 社工接案」。中學生與大學生的不同同意與使用環境需分開；社工只應讀到學生已批准的摘要。先對照實際產品版本是否可操作；若只是文件構想，寫「無法測試」，不可給成功分。語音與文字偏好、真人專業用途及機構接案能力仍需真人驗證。例子只供 Agent 1 初步提案，不能免去委託人審批。
