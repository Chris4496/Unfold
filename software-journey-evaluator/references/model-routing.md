# Agent 1 的 Pro／Flash 模型路由指引

「Pro」代表優先推理、跨來源整合與高風險決策品質；「Flash」代表低成本、低延遲、重複而可明確驗證的任務。兩者是本技能的策略標籤，**不是 WorkBuddy 特定模型 ID，也不是對實際供應商型號的保證**。首次 Agent 1 啟動由主 agent 按預設 Pro／可用高推理路由決定；Agent 1 在報告中仍需填寫自己的實際路由與後續建議。主 agent 已運行的模型無法事後切換，對主 agent 的建議僅供下一輪參考。實際子代理調用時先檢查當前環境可用的模型、路由別名與選擇能力；若只支援 `reasoning`／`lite`，可暫映射為 Pro／Flash，並在報告上寫「推理／輕量近似，非特定型號」。無逐代理指定能力時記錄「實際：Auto／預設」，請委託人選擇是否接受，不能偽稱模型分派成功。

預設是產品可用後的自然角色體驗；Agent 1 唯讀分析程式碼並提出 Persona／情境。技術驗證不是角色模擬的前置；Agent 2 與工程角色只在工具限制需要時適用。

## 決策順序

1. 對每個 agent 的每個任務判斷：錯誤的後果、推理／跨文件複雜度、風險、是否有機器可驗證成功條件、是否需要大量重複。
2. 高後果或含糊跨角色流程用 Pro；明確、可重跑、有檢查點的低風險任務用 Flash。一次多階段旅程可讓同一角色的常規步驟走 Flash，遇授權與模糊摘要時升到 Pro；若執行環境只支援每個 agent 一個模型，按其最關鍵任務決定整個代理的路由。
3. 在旅程報告中逐一列出模型建議與預算理由，再經委託人確認；不得在測試後悄悄降低模型以降低成本。

## 預設建議（由 Agent 1 可依個案調整）

| 角色 | 預設 | 為何 | 升級／降級條件 |
| --- | --- | --- | --- |
| 主 agent | Flash | 清晰格式下的對話、報告轉交及匯整；不作獨立產品判斷。 | 大量相互矛盾結論需要跨報告歸納時建議 Pro，需保留來源。 |
| Agent 1 旅程分析 | Pro | 從程式碼／文件推導產品理解、Persona、開放目標與交接；分開研究者知識與角色知識。 | 僅單頁低風險產品且流程明確，可提 Flash，寫理由。 |
| Agent 2 MCP 判定 | Pro | 取捨現有工具、可觀察性、資料暴露及工程邊界。 | 純工具清點可 Flash；必要性結論仍由 Pro 或人工復核。 |
| 自然使用者 agent | Pro | 維持 Persona，自行探索並記錄期待、反應與評價；只用 UI。 | 短、低風險情境可建議 Flash，需記錄品質取捨。 |
| 單一路徑使用者 agent（另行要求驗證時） | Flash | 操作步驟少、成功條件明確、可用事件紀錄核對。 | 私隱權限、模糊文案、敏感摘要、衝突或失敗恢復時用 Pro。 |
| 複雜使用者 agent | Pro | 多步情境、自由輸入、取消／修正與角色交接需要推理。 | 測試拆成明確低風險小任務後可用 Flash。 |
| Agent 3 流程監控 | Flash | 逐步核對檢查點、事件是否存在與有效性標籤。 | 日誌相互矛盾、權限爭議、監控是否已失效的判斷升 Pro。 |
| Agent 4 交接評核 | Pro | 跨角色比對發送、接收、同意、內容忠實與未完成狀態。 | 僅核對結構化的送達與接收事件，可用 Flash，但複雜交接由 Pro 復核。 |
| developer agent（按需） | Pro | 工具契約、權限設計與測試接口改動有安全風險。 | 簡單模板化代碼可 Flash 起草，仍由 Pro 或獨立 reviewer 審查。 |
| reviewer agent（按需） | Pro | 與 developer 分離，審核缺陷、權限與資料暴露。 | 不建議降級；若無可用 Pro，需告知委託人風險及另安排人工審查。 |

## Agent 1 報告中的路由列

`agent_id | 任務／場景 | 建議 Pro/Flash | 判斷依據 | 實際模型 ID／別名（待啟動核實） | 升級觸發 | 是否可降級 | 預算／品質權衡`

如有多個同類使用者，按任務風險分配，不因是中學生、社工等角色名稱而僵化配置。涉及真實敏感資料時，不靠升到 Pro 來解決資料使用權限問題；先停止、隔離或請合資格人士處理。檢查供應商實際支持的模型與逐代理派發能力，不將路由別名 `reasoning` 和 `lite` 寫成提供者保證的「Pro」及「Flash」型號。
